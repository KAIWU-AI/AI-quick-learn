# 从任意代码库到可解释的架构

先回答“谁发出什么、谁处理、何处保存、结果如何返回”。不按文件数量画节点，也不把包依赖等同部署关系。

1. 阅读仓库指引、入口README、已有架构图和设计文档。只读源码；不启动被分析程序、读取`.env`或云账号。
2. 沿一个具体业务请求追踪入口/路由、校验与授权、领域服务、数据库/缓存、队列/worker、外部服务、响应。实际异步分发与同步调用用不同边类型。
3. 在`sources`中记录相对文件路径、符号或行号，说明是代码、设计或示例。每个node/edge引用至少一条证据。
4. 合并实现上紧耦合、观众无需分开的节点。总览最多12节点、24边；更大架构拆为“总览+若干子系统工程”。
5. 节点标题强调职责；底层技术只有在形成架构亮点时才写。协议写在关系标签上，不到处重复。
6. planned节点必须保持“规划”标识；涉及它的连接也标planned。当前flow不得通过planned关系。
7. 图中的位置、色彩、流速与实例个数是视觉示意，不代表吞吐量、延迟、机房位置或部署数量。
8. 将用户确认的架构保存为`architecture.json`，再build。工具生成的页面是可视化产物，不是事实来源。

通用叙述模板（**分镜说明，不是要生成的语音**）：

- **请求旅程：**用户入口发出请求→验证→核心处理→数据访问→结果返回。
- **异步流水线：**接收→队列→并行/轮询worker→写入成果→回报状态。
- **本地/云边界：**用户端控制本地资源，云端提供远程计算；只画代码实际允许的跨界访问。
- **模块依赖：**一个核心模块与多个职责接口配合；用`agent`或`cluster`表达内部计算，不给普通服务强贴AI标签。

代码证据不足时保留疑问，勿从模块名推导出并不存在的调用链。给用户审查数据后再导出。
