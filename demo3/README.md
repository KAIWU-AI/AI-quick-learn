# Demo 3：第一个代理循环与多个工具

**新概念：工具执行与反馈构成代理循环。** Demo 1 直接请求 API，
Demo 2 通过消息历史实现多轮对话记忆，尚不使用工具。本课在保留历史的基础上，
首次加入工具定义、本地分派和自动继续请求，直接提供三个职责明确的工具。
模型选择工具与参数，Python 负责验证、执行和回传；不使用 LangChain 等代理框架。

与等待用户下一句的普通对话不同，代理把工具执行结果作为下一轮的反馈：
模型看到刚才采取的行动和结果后，可以继续查询、计算，或给出最终回答。
这在概念上对应本地 `learn-claude-code` 第一课的核心代理循环，
这里用 Responses API 和只读课程工具演示，不照搬其工具或消息协议。

## 运行

先按[根目录 README](../README.md) 安装依赖、配置客户端环境，在仓库根目录执行：

```powershell
python -m demo3
python -m demo3 "先查询全部课程详情，再用工具计算总时长，推荐中文学习顺序。"
python -m demo3 --max-steps 6
python -m demo3 --output demo3/result.html
```

可选位置参数替换默认问题；`--max-steps` 默认 `8`，取值 `1..12`，
限制的是 API 请求轮数，不是工具调用次数。达到上限仍未拿到最终回答会报错，
不会把中间结果伪装成任务完成。实际 API 请求需要根目录说明中的有效配置，
可能产生费用。

## 看见整个 Agent Loop

运行时自动生成 `demo3/result.html`，在浏览器直接打开即可。`--output` 可更改路径；每个事件后更新文件，运行中刷新页面可查看最新轨迹。

看板将**整体控制流、实际轮次和单步数据**放在一起：

- 顶部显示最终答案、模型请求数、工具执行次数、已报告 token 总量与运行耗时。
- 流程图标明“模型 → 工具 → 历史 → 下一轮模型”的反馈闭环，以及“不再调用工具 → 最终回答”的出口。
- 每轮卡片显示实际执行的工具与该次 API 耗时；点击可定位请求。模型决定真实轮次和工具批次，看板不预设固定路径。
- 时间线完整记录用户输入、请求、返回、历史写入、每次工具调用、每次工具结果和最终回答。支持播放/暂停、变速、上一步/下一步、进度条定位与事件筛选；回放**不会再次调用 API 或工具**。
- 工具参数与结果渲染为可展开的 JSON 树，`call_id` 提供双向跳转，能核对“哪个调用产生哪个结果”。请求里的完整 `input` 与历史快照展示反馈何时真正传入下一轮。

一轮可以请求多个工具，但本地始终顺序执行。工具错误用异常样式标出，修正成功后整次运行仍可完成；请求失败、返回不完整、无文本或轮数耗尽则明确显示失败，保留中间结果，不假造最终答案。配置错误也会生成错误页面，命令仍以非零状态退出。

观测代码在共用的 `demo_visualizer/` 中；循环、分派与历史维护仍留在本课 `__main__.py`。JSON 树沿用 Demo 1 的字段解读与转义。页面不依赖网络或外部资源；无 JavaScript 也能按顺序读全部事件。加密推理状态被遮蔽，但输入、回答及工具数据仍可能敏感。默认报告已加入 `.gitignore`；自定义输出路径请自行排除。

## 三个工具分别做什么？

| 工具 | 输入 | 输出与职责 |
| --- | --- | --- |
| `list_courses` | 空对象 `{}` | 只列出 `course_id` 与标题，**不提供时长** |
| `get_course` | `course_id`：`api`、`memory` 或 `tools` | 查询标题、分钟数和先修课程 ID |
| `sum_minutes` | `minutes`：1–10 个整数 | 计算并返回 `total_minutes` |

目录是嵌入代码的**虚构、确定性教学数据**：API 入门 20 分钟、多轮对话记忆
30 分钟、多工具 Agent Loop 40 分钟。先修关系为 `api → memory → tools`。
课程名称与三个 Demo 对应，时长只是供计算练习使用的示例值。
刻意把“发现课程”“查询详情”“计算总数”分开，观察工具之间的数据依赖。

## 从对话历史到行动反馈循环

```text
用户问题 → Responses API
             ↓
        保存完整 output
             ↓
        有 function_call？
          ├─ 有：逐个验证并执行 → 追加全部 function_call_output → 下一轮
          └─ 无：检查非空 output_text → 打印最终回答并返回
```

历史不仅记录用户与模型的文字，还要记录模型发出的工具调用及对应结果。
每轮都回传这些历史，模型才知道已经查过哪些课程、拿到了哪些分钟数，
并据此决定下一步行动；工具本身不会自动请求模型，继续请求由 Python 循环负责。

`response.output` 是数组，可能包含 `reasoning`、`message`、
`function_call` 等项目，不能只保存最终文本或筛出工具调用。代码逐项通过
SDK 的 `model_dump(mode="json", exclude_none=True)` 转换并完整加入历史；
类型 `cast` 只帮助类型检查，不改变内容。`store=False` 下由本地维护上下文，
并通过 `include=["reasoning.encrypted_content"]` 请求可回传的加密推理内容；
这些内容不打印，也不尝试解读。

执行结果使用 Responses API 的 `function_call_output`，用原调用的
`call_id` 配对；它不是旧 Chat Completions 的 `role="tool"` 消息。
模型可以在一轮批量请求多个调用，也可以重复调用工具；本地分派器始终
**顺序执行**，把这一批的全部结果追加后才进行下一次 API 请求。

## 应当观察什么？

默认问题要求先列目录，再查询全部三门课程，最后用 `sum_minutes` 求和。
**以下是预期路径，不是实际联网运行记录：**

1. 打印请求轮次，随后打印 `list_courses` 的名称、参数和结果。
2. 出现三门课程的 `get_course` 调用；它们可能集中在一轮，也可能分多轮。
3. 出现 `sum_minutes` 调用，例如 `{"minutes":[20,30,40]}`，返回
   `{"total_minutes":90}`。
4. 最终中文回答按先修关系排列课程，并说明总时长为 90 分钟。

具体措辞与批次取决于模型，提示词表达目标，不硬编码模型的调用轨迹。
终端只打印请求轮次、工具名称与参数、工具结果和最终文本，不打印推理内容
或访问凭据。

## 动手练习

把任务改成只学习前两门课程：

```powershell
python -m demo3 "先列出课程，只查询 api 和 memory 的详情，用 sum_minutes 求和并给出学习顺序。"
```

检查日志：是否先获取详情，再把查到的分钟数交给求和工具？预期总数为 50，
但要以实际日志验证，不只看最终回答。沿代码找出工具调用与结果加入
`history` 的两处位置，解释下一轮为什么同时需要它们。

## 边界与安全

- 三个工具全部只读：无 `eval`、Shell、文件访问或写入。
- 每个函数使用 `strict: true` 的 JSON Schema，所有参数都列为必填，
  且禁止额外键；无参工具也明确要求空对象。
- 本地仍验证参数：未知工具、非法或非对象 JSON、错误键、错误类型、
  未知课程都返回 `{"error":"..."}`。分钟数只接受 `0..480` 的整数，
  拒绝布尔值、空数组及超过 10 项的数组。
- 错误 JSON 会作为工具结果明确打印，并回传给模型尝试纠正，不假造成功。
  未完成的 API 响应、无工具调用且无有效文本、轮数耗尽则直接报错。
- 共用客户端与 CLI 错误处理由根目录 `demo_support.py` 提供；
  教学重点的工具定义、分派和循环仍完整保留在本文件中。
